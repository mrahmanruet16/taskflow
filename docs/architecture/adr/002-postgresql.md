# 002 — PostgreSQL as the Primary Database

# Decision

Use PostgreSQL 16 (the machine's existing native instance) as TaskFlow's primary database for all environments — development and (hypothetically) production. SQLite is used nowhere in this app; the one place SQLite was considered (the test suite) was explicitly rejected in favor of PostgreSQL too — see ADR 010.

# Context

The project brief specified PostgreSQL as a hard requirement and stated this machine already had a native PostgreSQL 16 instance running (verified in Phase 1: `pg_lsclusters` showed cluster `main`, port 5432, online; `pdo_pgsql`/`pgsql` PHP extensions confirmed present).

# Problem

Which database engine should back the application, and should development/testing use a lighter-weight substitute (SQLite) instead of the "real" production engine?

# Options Considered

## Option A — MySQL

Advantages:
- Extremely common in the Laravel ecosystem; most tutorials default to it.
- Slightly simpler default configuration for some hosting providers.

Disadvantages:
- Not what this machine has installed or what the project brief requires.
- Historically weaker standards compliance in some areas (e.g. `GROUP BY` semantics, `CHECK` constraint enforcement before MySQL 8.0.16) compared to PostgreSQL — not decisive here, but a real consideration if this were a green-field choice.

## Option B — SQLite (for everything, including "production")

Advantages:
- Zero setup — a single file, no server process.
- Fastest possible option for a single-user learning project.

Disadvantages:
- Explicitly not what the project brief asks for ("Use PostgreSQL").
- Weaker concurrent-write support (SQLite locks the whole database file for writes) — a bad fit for a multi-user app like TaskFlow (multiple project members writing tasks/comments concurrently), even at small scale.
- This machine's PHP build doesn't even have `pdo_sqlite` installed (discovered concretely in Phase 2.1 when the default Laravel test config failed with "could not find driver") — using it anywhere would require installing a new system package, which the project's Change Control rules require asking about first.

## Option C — PostgreSQL (native instance already running on this machine)

Advantages:
- Explicit project requirement.
- Already installed, running, and verified (Phase 1) — no new setup needed.
- Strong constraint enforcement (foreign keys, unique constraints, `NOT NULL`) enforced consistently — directly relevant to this project's teaching goal around database-level integrity (see Failure Experiment 5, planned: temporarily remove a foreign key constraint and observe what invalid data becomes insertable).
- Mature, first-class Laravel driver (`pgsql`) with no functional gaps relevant to this app.

Disadvantages:
- Slightly heavier setup than SQLite for a brand-new environment (a real server process, not just a file) — irrelevant here since it was already running before this project started.

# Decision Made

Option C — PostgreSQL, using the existing native instance.

# Why

This was a project requirement, not just a preference, and the environment was already correctly provisioned for it (verified, not assumed, in Phase 1's bootstrap checkpoint). Using anything else (even temporarily, "just for convenience") would have meant working against both the explicit brief and the actual state of the development machine.

# Consequences

- Every migration in this app (`projects`, `tasks`, `project_user`, `activity_logs`, `comments`) uses PostgreSQL-native column types and constraint syntax as generated by Laravel's schema builder (`bigserial` primary keys, real foreign key constraints with `ON DELETE` behavior — `cascadeOnDelete()`/`restrictOnDelete()`/`nullOnDelete()`, all documented per-table with reasoning in each migration).
- Status/priority/role fields (`ProjectStatus`, `TaskStatus`, `TaskPriority`, `ProjectRole`) are stored as plain `VARCHAR` columns with PHP-level backed-enum casting, NOT PostgreSQL's native `ENUM` type — a deliberate sub-decision: PHP enums give the same type-safety benefit at the application layer without a migration-unfriendly native DB enum (adding a new enum value to a Postgres native `ENUM` type requires `ALTER TYPE`, which is more disruptive than adding a new case to a PHP enum and a corresponding CHECK-free string column).
- A dedicated test database (`laravel_learning_test`, separate from the dev database `laravel_learning_dev`) was created specifically so automated tests could also run against real PostgreSQL rather than a substitute — see ADR 010 for the full reasoning.

# When We Would Reconsider This Decision

If a future related project in this learning series explicitly wants to teach MySQL-specific behavior, or if PostgreSQL-specific features actually used here (if any were to be added, e.g. `pgvector`) needed to be dropped for portability reasons — neither applies to TaskFlow as built.
